# Automation, scripts and future bolt-ons

The site should do the boring parts itself. Every script here is small, dependency-light Node ESM, runnable with `node scripts/<name>.mjs`, and safe to run repeatedly.

## Script conventions

- ESM (`.mjs`), Node 20+, standard library where possible. Add a dependency only when hand-rolling would be worse — YAML parsing and Markdown rendering qualify; string formatting does not.
- **Idempotent.** Running twice produces identical output.
- **Fail loudly.** Never guess a missing value; exit non-zero with the file and field named. A script that silently invents a duration is worse than no script.
- Generated files start with `<!-- generated by scripts/<name>.mjs — do not edit -->`.
- **No wall-clock values in output** (ADR-0010). Derive dates from content.
- Every script prints a one-line summary of what it wrote. Luke needs to see that it did something.
- `npm run build` chains them: index → `astro build` → podcast feed → validate → check-register. Sitemap and site RSS come from `@astrojs/sitemap` and `@astrojs/rss` rather than custom scripts.

## The script set

| Script | Does | Priority |
|---|---|---|
| `validate-content.mjs` | Cross-file checks Zod cannot do (taxonomy, slug/filename, duplicate GUIDs, `related` targets, transcript presence, Blob host) + built-HTML checks (h1, main, headings, alt, links, inline styles) | **Shipped** |
| `build-index.mjs` | Emits `public/content-index.json` — the keystone | **Shipped** |
| `check-register.mjs` | Fails on any class in built HTML not present in a template or component | **Shipped** |
| `build-podcast-rss.mjs` | Emits `podcast.xml` from `podcast.json` + episodes; idempotent | **Shipped** |
| `src/pages/feed.xml.js` | Site-wide `feed.xml` via `@astrojs/rss` | Soon |
| `@astrojs/sitemap` | `sitemap.xml` | Soon |
| `build-og.mjs` | Renders per-post OG images with Satori | When posts exceed ~10 |
| `audio-prepare.mjs` | ffmpeg wrapper: normalise loudness, encode to house bitrate, print bytes and duration for frontmatter | With first episode |
| `draft-linkedin.mjs` | Finds published items without a LinkedIn sidecar and scaffolds one | When repurposing starts |
| `check-links.mjs` | Verifies external links still resolve; reports rather than edits | Monthly |

`validate-content.mjs` and `build-index.mjs` are the load-bearing pair. Everything else is downstream of them.

## Where scripts run

1. **Locally** during authoring — fastest feedback.
2. **In CI** on pull request — a GitHub Action running `npm run validate`, failing the check on error. This is what actually stops drift, because it does not depend on anyone remembering.
3. **At build time** on Vercel for generated artifacts, so the deployed feed always matches the deployed content.

Do not put a generated file in git *and* generate it at build time. Pick one. Default: generate at build into `dist/`, gitignore the output. Exception: `public/content-index.json` is committed because scripts read it before build.

## Integration ladder — future bolt-ons

Ordered by value-to-effort for this site specifically. The rule throughout: **nothing gets added that Luke cannot debug or switch off in under ten minutes.** Each step is independently useful; do not skip ahead.

1. **Search** — client-side over `content-index.json` with a small index. No service, no key, works offline. Only outgrow this past a few hundred items.
2. **Email capture** — a single provider (Buttondown, Kit) with a plain HTML form posting to their endpoint. No SDK. The form markup is in `html-contract.md`.
3. **Post-to-LinkedIn assist** — keep it manual-with-a-draft-file. LinkedIn's API for personal posting is restrictive and the automation is not worth the auth complexity for one person posting weekly.
4. **Podcast distribution** — submit `podcast.xml` once; Spotify and Apple pull it. No integration to maintain.
5. **Comments / responses** — Giscus (GitHub Discussions) if wanted. No database, no moderation panel to run.
6. **Analytics beyond Vercel** — only if a specific question needs answering. Adding analytics without a question in mind adds weight and a privacy notice for nothing.
7. **Data-backed posts pulling live APIs** — the interesting one for a finance site, and the one to attempt last. Pattern when it comes: fetch at **build time**, commit a dated snapshot to `content/data/<slug>-<date>.json`, render from the snapshot. Never fetch from the browser at read time. This keeps pages fast, keeps them working when the API dies, and makes every published figure reproducible — which matters more on this site than freshness.

Each integration gets a decision record: what it does, what it costs, what breaks if it disappears, and how to remove it.

## Guardrail

Before adding any automation, answer: what happens when this breaks while Luke is not looking? If the answer is "the site is wrong and nobody notices", it needs a validator check first, or it should not be built.
