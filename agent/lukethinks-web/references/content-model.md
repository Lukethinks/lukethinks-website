# Content model

One shape, four flavours. Every piece of content on the site — article, learning note, research piece, episode — shares a common core so that indexes, feeds, related-links and LinkedIn drafts can be generated from a single pass over the content directory.

## Where content lives

```
content/
  site.json                    # name, URL, author, nav, audioHost
  podcast.json                 # channel-level podcast facts
  taxonomy.json                # controlled tag list
  articles/    <slug>.md       # Astro collection "articles"
  research/    <slug>.md       # collection "research"
  learnings/   <slug>.md       # collection "learnings"
  episodes/    <slug>.md       # collection "episodes"; show notes + audio metadata
public/
  transcripts/ <slug>.vtt
```

Each folder is an Astro content collection defined in `src/content.config.ts`. **That Zod schema is the contract** (ADR-0012); this document describes it, it does not compete with it. If they disagree, fix this document.

## Core frontmatter — required on everything

```yaml
---
title: "When Billion-Dollar AI Partnerships Meet Reality"
slug: "ai-partnership-accounting"        # kebab-case, matches filename, never changes
type: "article"                           # article | learning | research | episode
summary: "What happens when technology moves faster than the accounting rules."
published: 2025-10-04                     # ISO date
updated: 2025-11-02                       # optional, ISO date
status: "published"                       # draft | published | archived
lang: "en"                                # en | nl — default en (ADR-0008)
tags: ["accounting", "ai", "valuation"]   # from the controlled list below
---
```

`readingMinutes` is **not** a frontmatter field — `build-index.mjs` computes it into `content-index.json`.

Rules:

- **`slug` is permanent.** It is the URL, the filename, the `data-slug` hook, the RSS guid stem, and the link in every LinkedIn post already published. Renaming a slug requires a 301 in `vercel.json` in the same change. Slugs are the last URL segment; the prefix comes from the type (`/articles/`, `/research/`, `/learning/`, `/podcast/`).
- **`status: draft` never builds.** Drafts stay in the repo, excluded from indexes, feeds and sitemap.
- **Dates are ISO, no exceptions.** Human formatting happens at render time, in one place.
- **Do not invent metadata.** If you do not know a real date, duration or reading time, emit `TODO(luke)` and let the validator flag it. A wrong date in an RSS feed is permanent for anyone who already downloaded it.

## Controlled tag list

Free-text tags fragment instantly (`AI`, `ai`, `artificial-intelligence`). Tags live in `content/taxonomy.json`:

```json
{
  "tags": [
    { "id": "accounting", "label": "Accounting Standards", "description": "GAAP/IFRS mechanics" },
    { "id": "ai", "label": "AI", "description": "AI economics and tooling" },
    { "id": "fpa", "label": "FP&A", "description": "Planning and analysis practice" },
    { "id": "frameworks", "label": "Thinking Frameworks" },
    { "id": "experiments", "label": "Experiments" }
  ]
}
```

Adding a tag means editing this file. The validator rejects any tag not listed. This is deliberate friction — it keeps the taxonomy from being reinvented by whichever model wrote the last post.

## Type-specific extensions

Each content type adds its own fields on top of the core; see the relevant file in `content-types/`. The extensions are additive only — nothing overrides a core field's meaning.

## Derived files — generated, never hand-edited

Each carries a `<!-- generated by scripts/… — do not edit -->` banner.

| File | Built by | Contains |
|---|---|---|
| `public/content-index.json` | `build-index.mjs` | Every published item's core fields + computed reading time + counts, sorted by date |
| `sitemap.xml` | `build-sitemap.mjs` | All published URLs |
| `feed.xml` | `build-rss.mjs` | Site-wide article feed |
| `podcast.xml` | `build-podcast-rss.mjs` | Podcast feed (separate — different spec, see podcast doc) |
| `/tags/<id>` | `src/pages/tags/[id].astro` | One index page per tag |

`content-index.json` is the keystone: related posts, tag pages, homepage latest list, `.topic-count` numbers, and the LinkedIn backlog all read it. Inside Astro pages, prefer `getCollection()` directly; the JSON exists for scripts and client-side search.

## Relationships

```yaml
related: ["asc-323-equity-method"]   # explicit, curated — slugs only
series: "ai-economics"               # optional, groups a multi-part run
seriesPart: 2
```

Automatic "related by shared tags" is the fallback when `related` is absent. Curated beats computed; both beat nothing.

## Adding a new content type later

1. Create `content/<plural>/` and a `content-types/<type>.md` in this skill.
2. Add a collection to `src/content.config.ts` extending `core` or `prose`.
3. Add a row to the SKILL.md routing table and a golden template.
4. Extend `build-index.mjs` only if the type needs fields the core does not cover.

If step 4 requires touching more than one script, the type is probably a variant of an existing type. Prefer a `format` field over a new type.
